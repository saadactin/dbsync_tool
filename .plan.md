# Zoho full sync: execution detail UI and live-style progress

This document records the implementation that was completed for per-table Zoho execution logs, optimized log parsing, file fallbacks, and live-style updates via structured log lines.

## Problem

Runs completed successfully but Execution Details showed **Tables Progress 0/0**, **Rows 0**, and **No table logs** because `SyncExecutionLog` rows were never created from the actual log format (`zoho_full_optimized_*.log` MIGRATION SUMMARY).

## Root causes addressed

1. **Parser mismatch** — Only legacy lines (`+N / -M`) were parsed. Optimized summary lines (`ZOHO_* ... SUCCESS ... rows ... s`) are now parsed.
2. **Wrong fallback** — Zoho runner now merges today's disk log text (`logs/zoho_full_optimized_{YYYYMMDD}.log`, then `logs/zoho_full_{YYYYMMDD}.log`, else `zoho_increment_*.log`) with subprocess stdout before parsing. This ensures the UI is populated even when stdout is non-empty but lacks MIGRATION SUMMARY lines.
3. **Duration column** — `verification_summary` set to `Duration: Xs` (success) or `NO_ACCESS`; template and polling JSON expose `verification_summary` for Duration/Verification columns.
4. **Live updates** — `subprocess.Popen` reads stdout line-by-line; lines starting with `ZOHO_SYNC_LOG v1|` create/update `SyncExecutionLog` rows during the run so the existing 2s polling UI can show new rows. On success, a final transactional parse from `disk_text + "\n" + stdout` replaces logs with the MIGRATION SUMMARY so results stay consistent.

# Step 4: explicit daily time (24-hour) for scheduled jobs

## Summary

Create Sync Job **Step 4** ([`create_step3.html`](dbsync_tool/sync_jobs/templates/sync_jobs/create_step3.html)) and **Job edit** ([`job_edit.html`](dbsync_tool/sync_jobs/templates/sync_jobs/job_edit.html)) now show separate **First run date** (`type="date"`) and **Run at (24-hour)** (`type="time"`, `step="60"`) when the schedule is Hourly, Daily, or Weekly. ## Backend

- [`validate_schedule_start_inputs`](dbsync_tool/sync_jobs/validators.py) combines `start_datetime`, or `start_date` + `start_time`, or defaults to “now” when both empty (recurring only).

# Schedule: every N hours vs daily at fixed time

## Summary

Incremental (and other) jobs can run on a **repeating hour grid** (every 1–24 hours from a first-run anchor) or **once per calendar day** at a fixed 24-hour time. The model field `SyncSchedule.interval_hours` (default **1**) controls the hour grid for `schedule_type='hourly'`. **Daily** behavior is unchanged: same local time each day.

## Semantics

- **Hourly + `interval_hours=N`**: Next due time advances by **N hours** on the anchor (same minute as the first-run anchor), not “N hours after the previous run finished.”
- **Daily**: Same wall-clock time each **calendar day** (handles DST differently than “every 24 hours” on the hour grid—use **Daily** for “always at 15:30”).

# Sync summary emails after execution

## Goal

Send a summary email after every sync execution (full or incremental), on both success and failure, with:
- migration path (`source -> target`)
- duration and status
- total rows added/synced
- completed/failed/changed table counts
- table-level highlights when available

## Recipient policy

- `ADMIN_EMAILS` from settings
- plus job creator email
- deduplicated and validated addresses only

## Design

- Added reusable summary payload builder:
  - [dbsync_tool/sync_jobs/services/execution_summary_service.py](dbsync_tool/sync_jobs/services/execution_summary_service.py)
- Added email sender service with defensive handling:
  - [dbsync_tool/sync_jobs/services/sync_email_service.py](dbsync_tool/sync_jobs/services/sync_email_service.py)
- Added execution completion hook in:
  - [dbsync_tool/sync_engine/executor.py](dbsync_tool/sync_engine/executor.py)

## Error-handling guarantees

- Email failures never fail the sync execution flow.
- Exceptions in email send are logged with execution/job context.
- If no table logs exist, email still sends top-level summary with a fallback note.
